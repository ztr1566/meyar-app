# PostgreSQL Database Layer Design

## Scope

Add the Phase 2 persistence foundation to the existing Fastify server without
changing the standalone frontend data flow. The layer includes local
PostgreSQL 16, Prisma ORM 7, a pooled Prisma PostgreSQL client, strict Zod
request schemas, deterministic fixture seeding, and integration tests.

The existing `docker-compose.yml` already provides a basic PostgreSQL 16
service and `.env.example` already contains the local connection shape. This
phase will keep those names and credentials stable while adding health and
pool settings where useful.

## Research Decisions

- Prisma 7.9.1 is the current package version at implementation time.
- Prisma 7 requires a PostgreSQL driver adapter, so runtime code will use
  `@prisma/adapter-pg` with one `pg.Pool` and one Prisma client instance.
- The pool will use a bounded default of 10 connections, a 5-second connection
  timeout, and a 5-minute idle timeout; these are application pool settings,
  not URL parameters.
- Prisma 7's `prisma-client` generator emits TypeScript. The repository already
  runs on Node 24, so generated TypeScript will use ESM imports with `.ts`
  extensions and Node's native type stripping; generated output is ignored and
  regenerated by `postinstall`/`db:generate`.
- Prisma CLI configuration will live in `prisma.config.js`, which keeps the
  requested `prisma/seed.js` workflow without introducing a TypeScript build.
- Zod 4 strict objects will reject unknown request keys rather than silently
  stripping them.
- Monetary fields remain Prisma `Float` because the Phase 2 contract explicitly
  requests `price Float` and `budget Float`; a future transactional billing
  layer should use exact decimal storage instead.

## Data Model

`prisma/schema.prisma` will use the `postgresql` provider and generate
application-visible CUID-compatible string IDs. Seeded fixture records provide
their existing IDs (`chef-1`, `recipe-1`, and so on) so all fixture foreign keys
remain deterministic; records created without an ID receive `cuid()` values.

Models:

- `User`: unique email and handle, password hash, profile fields, `Role` enum,
  verification, and creation timestamp.
- `Recipe`: author relation, recipe metadata, JSON ingredients and steps, tags,
  likes count, and creation timestamp.
- `Comment`: author and recipe relations, recipe deletion cascade, update
  timestamp, and the required `(recipeId, createdAt)` index.
- `SupplyItem`: supplier relation, inventory, price, status, and catalog data.
- `RFQ`: requester relation, budget, deadline, and status.
- `ChatConversation`: participant relations and ordered messages.
- `ChatMessage`: conversation, sender, receiver, content, read state, and
  creation timestamp.
- `Notification`: recipient relation, type, content, read state, and creation
  timestamp.

Every foreign key will have an index where it is not already covered by a
composite index. Conversation messages will cascade when their conversation is
deleted. Comments will cascade when their recipe is deleted as explicitly
required; user-owned records will use restrictive user relations until account
deletion policy is defined.

## Runtime Integration

`server/db/client.js` will export the singleton `prisma` client and a small
Fastify registration function. The function installs an `onClose` hook that
disconnects Prisma and ends the underlying `pg.Pool`. `server/app.js` will
register that hook, so both normal signal shutdown and test cleanup through
`app.close()` release database resources. No query will run during app
construction; the pool connects lazily on the first query.

`.env.example` will document `DATABASE_URL`, `DB_POOL_MAX`, and the existing
server settings. Prisma CLI will load `.env` through `dotenv` in
`prisma.config.js`; the server's existing `--env-file-if-exists=.env` scripts
continue to load runtime environment variables.

## Validation

Create focused schemas under `server/schemas/`:

- `auth.js`: strict register and login payloads with email, password, name,
  handle, and role constraints.
- `recipe.js`: strict recipe creation payload with bounded times/servings,
  supported difficulty values, non-empty tags, and structured JSON arrays.
- `comment.js`: strict comment payload with non-empty content and IDs.
- `rfq.js`: strict RFQ creation payload with positive budget, ISO deadline,
  requester ID, and bounded text fields.
- `index.js`: named exports for the schemas.

These schemas validate request shape only. Authentication, authorization,
ownership checks, and database existence checks remain endpoint concerns for a
later phase.

## Fixture Seeding

`prisma/seed.js` will import the existing ESM fixture index and normalize its
different presentation shapes into the relational models:

- Merge chef, demo-user, supplier, and chat-partner records into users,
  preserving known IDs and deriving deterministic local emails/handles only
  when fixtures omit them.
- Map recipe English display fields to the single persisted title/description
  fields and preserve ingredients, steps, and tags as JSON/arrays.
- Map supply catalog records to `SupplyItem` and nested supplier IDs.
- Map RFQ cards to requester-owned RFQs using the active fixture user.
- Flatten nested chat fixtures into conversations and messages.
- Attach notifications to the active fixture user and preserve their timestamps.

The script will use ordered upserts inside a transaction so it is safe to run
more than once and does not create duplicate fixture rows. Fixture-only users
receive deterministic non-login password hashes; real password hashing and
credential flows are outside this phase.

## Testing

`tests/schemas.test.mjs` will verify valid payloads parse and unknown keys or
invalid boundary values fail. `tests/db.test.mjs` will run against the configured
PostgreSQL database and verify:

- Prisma can connect and execute a trivial query.
- User, recipe, comment, and comment update CRUD works.
- Deleting a recipe cascades to its comments.
- The named `(recipeId, createdAt)` comment index exists in PostgreSQL.

Database tests use unique IDs per run and clean up their records in `finally`
blocks. The existing frontend and server tests remain unchanged except for
their normal app shutdown now also closing the database client.

## Commands

Add these package scripts:

```json
"db:generate": "prisma generate",
"db:migrate": "prisma migrate dev --name init",
"db:seed": "prisma db seed",
"db:studio": "prisma studio"
```

`npm run db:migrate` creates/applies the initial migration, `npm run db:seed`
loads the fixtures, and `npm run test` runs the complete test glob once the
local PostgreSQL service is available.
