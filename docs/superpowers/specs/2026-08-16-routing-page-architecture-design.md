# Root Landing and Feeds Route Design

## Decision

Keep the existing static multi-page architecture. Move the current feed page
from `index.html` to `feeds.html`, create a public landing page at
`index.html`, and add a Fastify `GET /feeds` route that serves `feeds.html`.

Do not add a client-side router or authentication guard in this change. The
feed remains public for now. Authentication can be added later without
changing the public route contract.

## Current Architecture

- `index.html` currently contains the feed markup.
- `js/pages/feed.js` renders feed content into DOM markers such as
  `feed-posts-container` and `stories-track`.
- `js/main.js` calls `FeedPage.init()` based on those markers and the current
  pathname.
- `server/plugins/static.js` serves static files and maps `/` to
  `index.html`.
- `scripts/update-all-navbars.mjs` generates the shared app header for the
  existing application HTML pages.
- `AuthPage` stores its simulated user only in memory and redirects successful
  authentication to `index.html`.

## Routing

### Root

`GET /` serves the new public landing page in `index.html`.

The landing page will not contain feed DOM markers and will not be treated as
the feed by `autoInitPage()`.

### Feed

`GET /feeds` serves `feeds.html`, which retains the existing feed markup and
page controller behavior.

`feeds.html` remains directly loadable for the repository's existing
`file://` workflow. Static links use the `.html` page target for that
compatibility, while the server exposes `/feeds` as the requested route.

### Authentication

No `/feeds` protection or session persistence is added. Login, registration,
and social-auth success redirects target `feeds.html`; the landing page offers
an explicit feed CTA and authentication links.

The root route does not smart-redirect authenticated users.

## Page and Navigation Structure

### Landing Page

`index.html` becomes a small public marketing page using existing Meyar
typography, color tokens, theme handling, and bilingual i18n. It will include:

- Public brand header with a logo link to `index.html`.
- Product value proposition and a concise set of platform benefits.
- CTA to `feeds.html`.
- Login and registration links to `auth.html`.
- Existing language and theme controls.

The landing page is not included in the generated authenticated app navbar.

### Feed Page

`feeds.html` keeps the existing feed HTML, search modal, interactive controls,
and query-parameter behavior. Only route-sensitive links and page metadata
change.

### Shared App Links

The shared navbar generator will use `feeds.html` for:

- App logo links.
- Desktop feed navigation.
- Breadcrumb feed links.
- Mobile drawer feed links.
- Bottom navigation feed links.

`auth.html` remains public and its home/back link targets `index.html`. The
direct feed link generated by `js/pages/chef.js` and successful auth redirects
will target `feeds.html`.

The generated navbar page list will replace `index.html` with `feeds.html`.

## Initialization and Active Navigation

Update `js/main.js` so feed initialization recognizes `feeds` and
`feeds.html`, as well as existing feed DOM markers, but no longer treats the
root or `index.html` pathname as a feed fallback.

Update `js/app.js` active-navigation mapping so `feeds` and `feeds.html` map to
the feed navigation key. The root landing page will not receive an app-nav
active state.

## Metadata

Add page-specific metadata to both entry pages:

- Landing title and description describing Meyar as a culinary platform.
- Landing OpenGraph type, title, description, and root URL.
- Feed title and description describing the discovery feed.
- Feed OpenGraph type, title, description, and `/feeds` URL.

Landing copy will use new Arabic and English translation keys in
`js/data/translations.js` so the existing language switcher remains
consistent.

## Verification

Update the static-page and server tests to cover the new page split:

- `index.html` exists and is a valid landing page.
- `feeds.html` exists and retains the feed markers and shared search modal.
- `GET /` serves the landing page.
- `GET /feeds` serves the feed page.
- Feed initialization is selected for `/feeds` and not for `/`.
- Feed links resolve without changing recipe query strings or other existing
  page targets.
- Existing translation, solid-surface, CSS, and asset integrity checks remain
  valid.

Run `npm run test` and `npm run build` after implementation. The build updates
the generated `js/bundle.js` and `css/output.css` using the repository scripts.
